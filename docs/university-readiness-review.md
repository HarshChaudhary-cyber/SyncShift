# University handover review — 27 September 2026

## Decision

Suitable for a supervised demonstration with synthetic data. **Not yet approved for a production university rollout or real student records.** This is a source review and automated verification, not a security certification or a claim that every UI interaction was tested.

The review covered authentication, tenant/role enforcement tests, scheduling, imports, the assistant, notifications, database migrations, Docker, CI and documentation. Existing uncommitted deployment and scheduling fixes were reviewed and included. Local credentials and databases must stay out of Git.

## Corrections included

- Removed the runtime CAPTCHA bypass for synthetic test tokens. The isolated test harness explicitly enables mocks; a running application does not.
- Enforced the configured CAPTCHA requirement on password login even when its secret is missing.
- Restricted CORS headers on errors to exact configured origins. A hostname containing `localhost` or `127.0.0.1` is no longer implicitly trusted.
- JWT creation now honors `ACCESS_TOKEN_EXPIRE_MINUTES`; it previously always issued seven-day tokens.
- Rejected passwords exceeding bcrypt's 72-byte input limit with a validation message instead of an internal error.
- Preserved explicit zero work-hour limits and transition buffers across profile, scheduling, analytics and assistant reads.
- Production email delivery failures now return failure and do not dump personal message content to console logs.
- Replaced the hardcoded September 2026 block start default with the creation date; corrected date-dependent test fixtures and a planner test that assumed all sessions fall in one calendar week.
- Isolated pytest from the developer's database and external AI/CAPTCHA credentials using a temporary database.
- Added a fresh-migration smoke check that exercises registration, profile retrieval and block creation against Alembic-created tables.
- Included the existing standalone production frontend image and public build arguments, backend migration entrypoint, and shell line-ending handling. Excluded all frontend environment files from the Docker build context.
- CI now provisions Redis and OCR tools and runs the migration smoke check; live-server scripts are explicitly excluded from ordinary CI.

## Suggested university acceptance walkthrough

1. Use synthetic accounts and a disposable database. Demonstrate student, faculty and administrator roles, including denied cross-role/cross-tenant access.
2. Create courses, sections and enrollments; draft, review and publish a timetable; verify the student calendar and notifications change correctly.
3. Add a shift, create a conflict, plan study time, change a recurring occurrence and verify no duplicate or lost events. Check zero work limits, overnight events and timezone boundaries.
4. Ask the assistant for app help and schedule facts. Move today's work to tomorrow, including a conflict rejection and a repeated command.
5. Import a clear CSV/ICS and a scanned timetable. Review uncertain entries, duplicates and conflicts before saving.
6. Test sign-out, rejected credentials, account recovery requirements, data export/deletion, and a backup restore in staging.

## Reproduce local checks

From `backend`, run `python -m pytest --ignore=test_live_docker_scenarios.py --ignore=test_live_image_upload.py` and `python verify_migrations.py`. Pytest uses a disposable database; live service tests need their documented runtime dependencies.

From `app`, run `npm ci`, `npm run lint -- --quiet`, `npm run build` and `npm audit --omit=dev`. These checks do not deploy the app or publish student data.
